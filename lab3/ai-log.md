# 大模型辅助开发记录

日期：2026-11-11。工具：本次 Codex 对话。以下记录实际使用、复核与修正过程。

## 输入和上下文补充

用户提供实验三任务：按实验二 UML 实现超过1500行代码，采用构建工具，使用大模型辅助开发，并通过 Git 管理本地与远程仓库。模型随后读取实验一成品 `requirements.md`、实验二类图、预约状态机、预约时序图以及设计报告，从中确定商品九状态、预约七状态、角色限制、幂等和原子提交等实现约束。

用户在远程连接遇阻后补充：“不要用代理，尝试直连”。后续远程操作按该约束执行。没有使用其他模型或把工作派发给独立 agent。

## 从需求到规约再到实现

先建立可检查的前置条件：普通账号才可参与交易；每个商品最多一条有效预约；确认只发生在24小时到期前；状态变化同时提交商品、预约、审计及通知待投递记录；新请求必须检查版本，原请求重放先做当前权限校验。

据此建立 schema 的外键、CHECK、部分唯一索引，再实现 Core 的统一鉴权和事务包装、服务组及 CLI。测试通过真实 SQLite 文件调用公共应用方法，不依靠伪造数据库接口来证明业务状态正确。

## 模型辅助内容

1. 功能代码生成：数据库结构、账号、商品、预约、管理、统计、消息、备份和命令行。
2. 单元及集成测试设计：幂等重放、权限、并发互斥、精确金额、到期边界、故障回滚和重启恢复。
3. 模拟用户操作：`tools/demo.py` 运行卖家发布→管理员审核→买家搜索/预约/取消→重新预约→卖家确认→买家完成→重放→统计流程。
4. 风格检查：实际运行 Ruff，修复导入顺序、长行和嵌套上下文等问题，再执行格式检查。
5. 代码异味处理：抽取重复鉴权、版本校验、审计、结果结构、消息事件等方法，按职责拆分文件。

## 发现的问题和修正

- 首次测试多数业务断言通过，但 Windows 临时目录清理失败。原因是 `with sqlite3.Connection` 只管理事务，不负责关闭连接。初始化改用 `contextlib.closing`，并以 ResourceWarning 作为错误重新验证，避免掩盖资源泄漏。
- 初稿登录限制没有保存15分钟统计窗口，审查需求后加入窗口起点与锁定时间；成功登录清零，并补充窗口过期测试。
- 初稿“撤回后旧审核”测试只测了草稿不能审核，未真正覆盖命名场景，修正为送审→撤回→用旧版本审核，验证冲突。
- 通过故障注入，验证审计写入或 outbox 写入失败均回滚预约和商品；通过竞争测试确认预约、取消/确认、完成/解除只能产生一个成功结果。
- Ruff 首轮报告长行，使用格式化和必要的 SQL 字符串拆分修正，最终日志保留实际结果。

## 人工复核

模型完成初版后，按 `database.py` → `core.py` → 业务服务 → `cli.py` 的顺序阅读代码，并在隔离数据库运行 42 项测试和演示脚本。复核重点包括：有效预约部分唯一索引、`BEGIN IMMEDIATE` 事务边界、请求重放与版本校验、商品/预约状态配对、审计与 outbox 的提交关系。逐项结果记录在 `review-checklist.md`。

复核发现文档与代码的一处差异：2.1 节原先把 `ItemReview` 说明为审核记录，而 `catalog.py` 在送审、撤回、审核、下架、归档和整改等操作中都会写入 `reviews`。报告已将该行改为“商品操作留痕”，业务代码保持不变，修改后 42 项测试仍通过。

完整可复跑证据保存在 `evidence/`；复核记录、测试结果和报告第 3.3 节可以相互对照。
